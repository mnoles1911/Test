2026-05-05 | Mining 3×3×3 carve collapsed to 1×1×1 on some voxels | `_terrain.to_local()` does a float matrix transform; with `transform.scale = 0.166667` (1/6 m), world `-0.166667` round-trips to `-0.999999...` rather than `-1.0`. `Vector3i` truncation then loses one voxel per edge, collapsing the 3×3×3 to 1×1×1. 2026-05-05 | Right-click smoothing produced no work on untouched terrain on first load | Zylann streams chunks for rendering before `CHANNEL_COLOR` is fully populated, so `tool.get_voxel()` returns 0 (air) on chunks the player can clearly see. `_tick_held_action` was reading the aim-point material first and bailing on null, so smoothing never ran until a swing had touched a nearby voxel. 2026-05-05 | VoxelMesherCubes wrote vertex colours but the StandardMaterial3D rendered terrain uniform brown | Default `vertex_color_use_as_albedo = false` on the `StandardMaterial3D` makes it ignore the per-vertex colours the mesher emits. 2026-05-05 | Setting `vertex_color_use_as_albedo = true` made terrain render nearly black | NOT byte order. `VoxelBuffer.CHANNEL_COLOR` defaults to **8-bit depth** (one byte per voxel), so the 32-bit packed RGBA values the generator writes get truncated to just the R byte — the alpha-byte mat_id alone, ≈0.012-0.016 on screen. Mesher byte order matches Godot's `Color.to_rgba32()` (R high, A low) — no encoding rewrite needed. Fix: instantiate a `VoxelFormat`, call `set_channel_depth(CHANNEL_COLOR, DEPTH_32_BIT)`, assign to `terrain.format` BEFORE handing the terrain to systems that read it. The `format` property is null by default and lives on `VoxelLodTerrain` itself. | #135
2026-05-05 | Calling `out_buffer.set_channel_depth()` inside `_generate_block` made terrain disappear entirely | Confirmed twice in this codebase: the per-block call invalidates the buffer's channel storage even when made on a fresh buffer before any writes. Symptom is "empty chunks, player falls through the world." Always set channel depth globally on the terrain's `format` resource — never per-block. | #135
2026-05-05 | Spent hours rewriting voxel encode + decode across 7 files on a wrong byte-order hypothesis | The actual bug was upstream of byte order (8-bit storage truncating 32-bit values, see #135 above). The mesher byte order matched what `Color.to_rgba32()` produced all along. Lesson: when a render pipeline goes black/garbage, do a single read-back diagnostic FIRST — print one packed voxel from `tool.get_voxel(known_pos)` and look at its hex value. If high bytes are zero, it's storage truncation, not byte order. A sub-second diagnostic would have ruled out the multi-file rewrite. | #135

2026-05-05 | Stutter ONLY when the player translates, not when the camera rotates | Translation-only stutter means something runs in response to player position change but NOT camera rotation. 2026-05-05 | `WaterChunkMesher.set_player_chunk` was iterating `(2*radius+1)^3` chunks per chunk transition | At `MESH_RENDER_RADIUS_M = 64m` and `CHUNK_SIZE_M ≈ 2.67`, that's `49^3 = 117,649` iterations every ~2.7 m of walking. Each iteration does dictionary lookups + AABB tests against every source region. Cost: ~50-150 ms per chunk transition, exactly matching the long-standing "walking stutters but camera rotation is fine" hitch. Fix: water surfaces are 2D planes at fixed Y values. Iterate only the 2D `(dx, dz)` ring at each unique source-region surface Y. With 2 source regions = 49 × 49 × 2 ≈ 4,800 iterations. ~24× faster, fits under 1 ms. General principle: when iterating chunks for an effect that lives on a known plane, never sweep the perpendicular axis. | #135
2026-05-05 | `print()` in voxel hot paths contributed to main-thread hitches | Even though Godot's `print` is thread-safe, the string formatting + ring-buffer sync isn't free. 2026-05-09 | Gemini Nano Banana 2 rejected texture-prompt blocks with a recitation filter | The filter trips when one prompt block stacks too many specific signals at once: hex codes + named genre ("voxel game block face texture for a medieval fantasy RPG") + heavy negation language ("no baked lighting, no cast shadows...") + imperative voice ("Generate a..."). It reads as "specific reproduction request" and refuses. **Fix**: split into two parts — a verbose SYSTEM PROMPT (paste once into the system/style/context field) carrying meta + tiling math + style language, and short pure-descriptive per-material prompts (paste into the main prompt field). 2026-05-09 | At 6 vox/m a "subtly distinctive" texture became a visible repeating grid | Each voxel face is ~16.7 cm; a 10 m wall repeats the tile 60+ times. Any single bright pebble, prominent vein, off-color patch, or asymmetric crack becomes an obvious gridded pattern the player can't unsee. Prompts must explicitly forbid dominant features and ask for **uniform fine-scale variation** — many small things of similar visual weight, not one distinctive thing. 2026-05-09 | Zylann blocky terrain rendered all white despite a fully-populated atlas + library .tres | The atlas, the per-cube tile coords, the per-cube material, and the library bake all looked correct in `blocky_library.tres` (file inspection confirmed `material_override_0 = SubResource(...)` and `tile_top = Vector2i(2, 0)` etc.). But at runtime, `model.get_material_override(0)` returned null and faces sampled UVs across the full 2048×2048 atlas (not just one 32×32 tile). **Root cause**: Zylann's gdextension exposes `material_override_0`, `tile_top`, `tile_bottom`, etc. via `_get_property_list` as DYNAMIC PER-SURFACE / PER-METHOD properties. `ResourceSaver` writes them to .tres (round-trip looks fine on disk), but `ResourceLoader` doesn't restore them — fresh model instances come back with defaults. **Fix**: re-apply tiles + materials at runtime in `World3DBootstrap._inject_atlas_materials_into_library()`. Walk the library's models, call `set_tile(SIDE_*, vec)` and `set_material_override(0, mat)` on each non-null cube, then `lib.bake()`. The single source of truth is the runtime injection, not the .tres. | tileset-KJNfH
2026-05-09 | `VoxelLodTerrain.material` silently overrode every per-cube `material_override_0` to render an empty `StandardMaterial3D` | World3D.tscn carried a leftover stub `VoxelTerrainMat` (just `roughness = 0.85`, no albedo texture) on the terrain node. 2026-05-09 | `.set("tile_top", Vector2i(2,0))` and `.set("material_override_0", mat)` silently no-op'd despite the property appearing in `get_property_list()` | The first build_blocky_library.gd guessed at API names AND used `.set()` for everything. Even the saved-but-correct property names didn't stick because Zylann gdextension routes those properties through method pairs (`set_tile(side, vec)` / `get_tile(side)`, `set_material_override(idx, mat)` / `get_material_override(idx)`). `.set()` writes to a virtual property bag that the gdextension reads from for serialization but not for the actual mesh build. **Fix**: always use `.call("set_tile", SIDE_*, vec)` and `.call("set_material_override", 0, mat)` for these.
